## 文脈

UI定義には、文字列への値の埋め込み（「`${user.name}`さん、カートに`${state.qty}`点」）、`visibleWhen`
プロパティによる条件分岐、リストに対する部分木の反復が必要です。いずれも、サーバが送ったデータと利用者が
変えた状態に対して、クライアント上で式を評価することを要求します。問題は、どこまでの表現力を許すかです。

この問いは利便性を超えた重みを持ちます。式はネットワークから届くからです。言語にできることは、侵害された
サーバが全端末にさせられることでもあります。

## 検討した選択肢

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. JavaScript を埋め込む（JavaScriptCore / QuickJS） | 表現力が最大です | サーバから送られた任意コードを実行することになり、設計上そのものがリモートコード実行です。Appleの審査ガイドライン上もグレーです。Androidには別途JavaScriptランタイムを積む必要があります。エディタでの静的検証も不可能です |
| B. JsonLogic | 既製の実装があります | JSONで書かれた式はエディタの画面上で人間に読めません。SwiftとKotlinの実装は保守が止まっています |
| C. CEL（Common Expression Language） | 仕様が公開されています | 実用に足る Swift 実装が存在せず、仕様もこの問題に対して大きすぎます |
| D. 小さな独自の式言語 | 文法を必要十分に絞れます。停止性を保証でき、エディタで補完と型検査ができます | 3つのランタイム分の実装が必要です |

## 決定

**案D**を採用します。`SpectreExpr` という名前の小さな独自の式言語で、仕様は
[`docs/spec/expression.md`](../../spec/expression.md) にあります。

この言語は**意図的にチューリング完全にしません**。ループ、ラムダ、再帰、ユーザ定義関数を持たず、
ホワイトリストに載った組み込み関数だけを呼べます。したがって、任意の式が有限時間で停止することが、
実行時の方針ではなく文法として保証されます。

## 根拠

案Aは無条件に退けます。式評価はSDUIにおいてもっとも攻撃面の広い箇所であり、サーバが侵害されたら任意のコードを
全端末で走らせられる、という状態を設計として作ってはいけません。

案Bと案Cは同じ観察で落ちます。どちらを採っても、結局 Swift 実装は自分たちで書くことになります。それなら、
受け継いだ文法よりも自分たちで定めた文法のほうが優れています。小さく保てるうえに、エディタが式を静的に
検証し、書きながら補完できるからです。

文法を絞ることには第二の見返りもあります。パーサは各言語600〜900行程度に収まり、評価の入力と出力はいずれも
純粋なJSONなので、3つの実装が一致することをゴールデンコーパスで機械的に検証できます
（[ADR-0008](../ADR-0008-conformance-testing-strategy/ADR-0008-conformance-testing-strategy-ja.md)）。
そのコーパスこそ、ADR-0001 がネイティブ2実装を受け入れるときに依拠している前提です。

## 代償

表現力が足りない場面は必ず来ます。そのときの逃げ道は言語を強くすることではなく、**サーバ側で計算済みの
値をドキュメントの `data` に入れて送ること**です。クライアント側の式を表示ロジックに限定し続けることが、
停止性の保証とエディタの静的検証を意味あるものに保ちます。

## 再検討のトリガー

作成者が繰り返し必要とするのに表現できず、かつサーバ側で事前計算するのも現実的でないパターンが現れた
時点で、文法を開き直します。開き直すのは文法であって、チューリング完全にしないという決定ではありません。
拡張はコーパスのケースを添えてホワイトリストに追加する形で行い、任意評価への抜け道としては決して入れません。
