## 文脈

Swift、Kotlin、TypeScript という3つのランタイムが、それぞれ式を評価し、バインディングを解決し、
アクションを適用し、申告されたケイパビリティに合わせてドキュメントを劣化させます。ADR-0001 がネイティブ
2実装を受け入れたのは、これらの挙動を機械的に縛れるという前提の上でした。この記録は、その前提を具体的な
形にしたものです。

## 検討した選択肢

- **A. ランタイムごとに独立して単体テストを書き、**一致はレビューで確認する。
- **B. 実装非依存の共有コーパスを置き、**各ランタイムのテストがそれを読んで実行する。
- **C. プラットフォーム間のスクリーンショット比較**を一致確認の主軸にする。

## 決定

**案B**を採用します。`spec/conformance/` に、実装非依存のJSONケースを置きます。

| コーパス | 入力 | 期待出力 |
| --- | --- | --- |
| `expr/` | 式の文字列とスコープ | 評価結果のJSON値、またはエラーコード |
| `binding/` | ドキュメントと状態 | 解決済みのプロパティ値 |
| `actions/` | 状態とアクションの列 | 遷移後の状態と、発火した副作用の列 |
| `layout/` | ドキュメント | レイアウト計算前の、正規化された描画ノード木 |
| `compat/` | ドキュメントとケイパビリティの申告 | 劣化後のノード木 |

各クライアントSDKのテストは、このコーパスを直接読んで実行します。**コーパスを拡張せずに仕様を変更する
ことは禁止**で、これは継続的インテグレーションで強制します。

視覚的な検証は意図的に別建てにします。iOSは `swift-snapshot-testing`、Androidは Roborazzi、Webは
Playwright です。これらはプラットフォーム間の一致を求めません。1つのプラットフォームのなかでの回帰を
検出するためのものです。

## 根拠

案Aは、一致するかどうかを2つ目のテストを書く人に委ねてしまいます。それはまさに、ネイティブ2実装を
現実的な選択にするために ADR-0001 が防がなければならないドリフトです。共有コーパスは、一致を意図から、
ビルドが確認できる事実へと移します。

案Cは2つの異なる問いを混同しています。Swift と Kotlin が `a ?? b` を同じに評価するかは、正解が1つある
意味論の問いであり、ピクセルはそれを尋ねる手段として不適切です。変更後も画面が正しく見えるかは視覚の
問いであり、プラットフォームごとに答えます。SwiftUI と Compose にピクセル単位の一致を求めるのは、
不可能を求めることだからです（[ADR-0005](../ADR-0005-editor-stack/ADR-0005-editor-stack-ja.md) は、
エディタのキャンバスについて同じ区別をしています）。

## 代償

コーパスは独自のレビュー基準を持つ保守対象の成果物になり、仕様変更のたびに、コーパスがない場合より前払いの
費用がかかります。その費用こそが狙いです。挙動を変える変更のなかで一度払うことで、一方のプラットフォーム
だけが違う劣化をするという本番の事故で繰り返し払うことを避けます。

各ランタイムにはコーパスを読むハーネスが必要で、作って動かし続けるべきテスト基盤が3つ増えます。

## 再検討のトリガー

どのコーパス分類でも捕まえられなかった種類のランタイム間の不一致が本番で見つかった時点で、コーパスが
カバーする範囲を見直します。そのときの対応は分類を追加することであって、この方式をやめることではありません。
