# 技術選定

ADR (Architecture Decision Record) 形式。各決定は「文脈 → 選択肢 → 決定 → 根拠 → 代償と再検討の条件」で記述する。

前提として置いた制約（未確認のものは [roadmap.md](roadmap.md) の未決事項に再掲）:

- ライブラリは**既存のホストアプリに組み込まれる**。バイナリサイズと依存の少なさは機能より優先度が高い。
- UIを編集するのは**エンジニアではない担当者**（企画・マーケ・CS）を想定する。したがってコンポーネントは閉じた集合で、自由なスタイリングは許さない。
- 対象は iOS / Android のネイティブアプリ。Web は**編集用インタフェース**であってレンダリング先ではない。
- 想定規模は数十〜数百画面、日次で数回の公開。ミリ秒単位の低レイテンシ配信ではなく、CDNキャッシュ前提でよい。

## ADR-0001: クライアントのレンダリング方式

### 文脈

同一のUI定義を iOS と Android で同じように描画する必要がある。実装をどこまで共有するかが最初の分岐点。

### 選択肢

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A. ネイティブ2実装 | SwiftUI と Jetpack Compose で個別に実装 | 描画品質・アニメーション・アクセシビリティが最良。追加依存ゼロ。ホストアプリのデザインシステムと自然に混ざる | 同じロジックを2回書く。挙動のドリフトが起きる |
| B. Kotlin Multiplatform コア + ネイティブUI | パース・式評価・状態管理をKMPで共有、描画のみネイティブ | ロジックのドリフトが構造的に起きない | iOSに ~1.5–3MB の Kotlin/Native ランタイムが乗る。Swift側のAPIがObjC経由で不格好になりラッパが要る。iOSチームにGradle/KMPのビルド運用を強いる |
| C. Flutter / React Native | 描画ごとクロスプラットフォームフレームワークに載せる | 実装は1つ | ライブラリのために巨大なランタイムをホストアプリに強制する。ネイティブ画面との混在が難しい。**組み込みライブラリとしては論外** |
| D. WebView | HTMLを描画 | 実装は1つ、更新も容易 | ネイティブの操作感が出ない。スクロール性能・アクセシビリティ・フォントスケーリングが劣化する |

### 決定

**A. ネイティブ2実装**を採用する。共有するのはコードではなく **(1) 機械可読な仕様、(2) 仕様から生成された型、(3) 全ランタイム共通の適合性テストコーパス** の3点とする。

### 根拠

- C と D は「組み込みライブラリ」という前提と両立しない。ホストアプリにランタイムを強制する時点で採用障壁が跳ね上がる。
- 争点は実質 A と B。共有できるロジックの実体は「JSONのデコード」「式評価」「状態ストアとアクション適用」の3つで、コード量はおよそ2,000〜3,000行にとどまる。このうちデコードと型は**マニフェストからのコード生成**でドリフトを消せる（ADR-0002）。残る式評価は、入出力がともに純粋なJSONなので**ゴールデンテストのコーパス**でピン留めできる（後述の適合性テスト）。
- つまり B が防ぐドリフトの大半は、A + 生成 + コーパスでより安く防げる。一方で B の代償（iOSのバイナリ肥大とビルド運用）は消せない。
- レンダラ本体（ノード木 → SwiftUI/Compose）は、どのみちプラットフォーム固有で共有できない。ここが全体の実装量の大半を占める。

### 代償と再検討の条件

- 式評価・状態遷移の仕様変更のたびに2箇所を直す必要がある。コーパスが通らないCIで担保する。
- **再検討トリガー**: 適合性コーパスの失敗が四半期に3件を超える、または共有ロジックが5,000行を超えた場合、コア部分のみ KMP へ移行する（レンダラはネイティブのまま。B への部分移行は後からでも可能な設計にしておく）。

### 対象バージョン

- iOS 16+ / SwiftUI。UIKitホスト向けに `UIHostingController` ラッパを同梱する。
- Android minSdk 24 / Jetpack Compose。View システムのホスト向けに `AbstractComposeView` ラッパを同梱する。

## ADR-0002: コンポーネントマニフェストを単一の情報源にする

### 文脈

同じコンポーネント定義が、JSON Schema・iOSの型・Androidの型・エディタのパレット・インスペクタのフォーム・ドキュメントの6箇所に現れる。手書きで同期させると必ずずれる。

### 選択肢

- A. 各所で手書きし、レビューで同期を守る
- B. 型定義をどれか1つの言語（例: TypeScript）で書き、他を生成する
- C. 言語中立の宣言的マニフェスト (JSON) を情報源とし、すべてを生成する

### 決定

**C** を採用する。[`spec/component-manifest.json`](../spec/component-manifest.json) を情報源とし、以下を生成する。

```
spec/component-manifest.json
   ├─→ spec/schema/document.schema.json   (サーバ・エディタでの検証)
   ├─→ packages/manifest/src/types.ts     (エディタ/サーバの型)
   ├─→ clients/ios/.../Generated/*.swift  (Codable な型と列挙)
   ├─→ clients/android/.../generated/*.kt (kotlinx.serialization な型と列挙)
   ├─→ エディタのパレット + プロパティインスペクタ (実行時にマニフェストを読む)
   └─→ docs/spec/components.md
```

### 根拠

- マニフェストには型情報だけでなく**エディタ用のメタデータ**（カテゴリ、アイコン、インスペクタのウィジェット種別、許可される子コンポーネント、既定値）が必要で、これは TypeScript の型システムでは表現しきれない。B ではメタデータを別管理する羽目になる。
- インスペクタのフォームをマニフェストから実行時生成すると、**コンポーネント追加時にエディタのコードを一切書かなくてよい**。これは運用上いちばん効く。
- 生成されるのは型とデコーダまで。レンダラ本体は手書き（生成コードで描画まで賄おうとすると表現力が足りずに破綻する）。

### 代償

- マニフェストのスキーマ自体を設計・維持する必要がある（メタスキーマ）。
- 生成コードをコミットするか都度生成するかの運用判断が要る → **生成物はコミットする**。iOS/Androidの開発者が Node のツールチェインなしでビルドできることを優先し、CIで「生成し直して差分がないこと」を検証する。

## ADR-0003: UI定義の表現形式

### 選択肢

- A. JSON + JSON Schema
- B. Protocol Buffers / FlatBuffers
- C. 独自DSL (テキスト)

### 決定

**A. JSON**。ワイヤ上は gzip/brotli 圧縮。スキーマ検証は JSON Schema (draft 2020-12)。

### 根拠

- WYSIWYGエディタが編集する対象そのものであり、**人間が読めてdiffが取れる**ことの価値が大きい。バージョン管理・レビュー・ロールバック・障害時の目視確認すべてに効く。
- CDNキャッシュ + brotli で、想定される文書サイズ（1画面あたり5–50KB）ではバイナリ形式との差はレイテンシに現れない。
- B はスキーマ進化が硬く、「未知のフィールドを持つノードをどう扱うか」という SDUI の核心（ADR-0006）を扱いにくい。C はエディタとの往復（パース → 編集 → 再シリアライズ）でコメントや整形が壊れる。

### 補足

将来サイズが問題になった場合の逃げ道は残す: ドキュメントは `Content-Type` でネゴシエートし、`application/vnd.spectre.doc+json` の他に `+cbor` を追加できる構造にする（構造は同一、符号化のみ差し替え）。

## ADR-0004: 式言語とデータバインディング

### 文脈

`「${user.name}さん、カートに${state.qty}点」` のような文字列補間、`visibleWhen` の条件分岐、リストの反復が必要。どこまでの表現力を許すか。

### 選択肢

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. JavaScript を埋め込む (JavaScriptCore / QuickJS) | 表現力は最大 | **サーバから送られた任意コードを実行する** = リモートコード実行。Appleのガイドライン上もグレー。Androidに別途JSランタイムを積む必要。エディタでの静的検証が不可能 |
| B. JsonLogic | 既製実装がある | JSONで書く式はエディタのUI上で人間が読めない。Swift/Kotlin の実装が保守されていない |
| C. CEL (Common Expression Language) | 仕様が公開されている | Swift実装が実質不在。仕様が想定より大きい |
| D. 独自の小さな式言語 | 文法を必要十分に絞れる。停止性を保証できる。エディタで補完・型検査ができる | 3ランタイム分の実装が必要 |

### 決定

**D. 独自の小さな式言語 `SpectreExpr`**。仕様は [docs/spec/expression.md](spec/expression.md)。

意図的に**チューリング完全にしない**: ループなし、ラムダなし、再帰なし、ユーザ定義関数なし。組み込み関数のホワイトリストのみ。これにより任意の式が有限時間で停止することが構文上保証される。

### 根拠

- A は却下が確定的。SDUIで最も攻撃面が広くなる箇所であり、「サーバが侵害されたら任意コードが全端末で走る」という状態を作ってはならない。
- B/C を採らないのは、**どのみち Swift 実装を自前で書くことになる**から。それなら文法を自分で決めて小さく保ち、エディタでの静的検証と補完を効かせたほうがよい。
- 文法を絞ることでパーサは各言語 600〜900行程度に収まる。入出力が純粋なJSONなので、**ゴールデンコーパスで3実装の一致を機械的に検証できる**（ADR-0001の前提）。

### 代償

- 表現力が足りない場面が必ず来る。逃げ道は「式を強くする」のではなく **サーバ側で計算済みの値を `data` に入れて送る** ことを原則とする。クライアントの式は表示ロジックに限定する。

## ADR-0005: WYSIWYGエディタの技術スタック

### 決定

| 領域 | 採用 | 理由 |
| --- | --- | --- |
| フレームワーク | React 19 + TypeScript + Vite | エコシステムと採用可能性。マニフェスト由来の型をそのまま使える |
| ドラッグ&ドロップ | `dnd-kit` | キーボード操作とスクリーンリーダに対応。`react-dnd` は保守が停滞し、HTML5 DnD由来の制約が多い |
| 状態管理 | Zustand + Immer | ドキュメント木の編集に対して Immer の**パッチ列がそのまま undo/redo と協調編集の基盤**になる |
| キャンバス | DOM (Reactコンポーネント) | Canvas/WebGL 描画は選択・テキスト編集・アクセシビリティを全部自前で作ることになり割に合わない |
| フォーム | React Hook Form + マニフェスト駆動の動的生成 | インスペクタはコンポーネント追加時にコードを書かずに済ませる (ADR-0002) |
| サーバ通信 | TanStack Query + WebSocket (プレビュー同期) | |

### キャンバスの忠実度という問題

Webキャンバスは**3つ目のレンダラ**になる。SwiftUI/Compose と完全一致させることは原理的に不可能（フォントメトリクス、行分割、スクロール挙動）。

方針を2段構えにする:

1. **近似プレビュー (Web)** — 編集中の高速フィードバック用。「近似である」ことをUI上で明示する。
2. **実機ミラー (Device Preview)** — エディタが下書きドキュメントを WebSocket でブロードキャストし、実機アプリの開発者モード / 専用プレビューアプリが受信して**本物のレンダラで**描画する。QRコードでセッションに接続する。公開前の確認はこちらを正とする。

実機ミラーを「あとで付ける機能」ではなく **M2の必須要件**とする。これがないと編集者はWeb上の見た目を信じて公開し、実機で崩れる、という事故が必ず起きる。

### 協調編集

v1では **CRDT を採用しない**。ドキュメントに `version` を持たせた楽観ロック + 「他の人が編集中」のプレゼンス表示にとどめる。想定利用者数（1画面を同時に触るのは1〜2人）に対して Yjs 等の導入コストと、木構造のマージ結果が意味的に壊れうるリスクが見合わない。

## ADR-0006: バージョニングと前方互換性

### 文脈

SDUI の失敗はほぼすべてここで起きる。**アプリのバージョンは強制更新しない限り古いまま残る**。半年前のアプリが、今日追加したコンポーネントを含むドキュメントを受け取る。

### 決定

3層で守る。詳細は [docs/compatibility.md](compatibility.md)。

1. **ケイパビリティネゴシエーション** — クライアントは対応スキーマバージョンとコンポーネント集合のハッシュをリクエストヘッダで申告する。サーバは古いクライアントに対して互換な木を返す。
2. **ノード単位のフォールバック** — 各ノードは任意で `fallback`（代替ノード）と `optional`（未知なら省略してよい）を持てる。未知の `type` に遭遇したクライアントは、フォールバック → 省略 → プレースホルダ の順に劣化する。**決してクラッシュしない**。
3. **加算のみのスキーマ進化** — マイナーバージョンではプロパティの追加のみ。削除・意味の変更はメジャーバージョンとし、移行期間中は両バージョンを並行配信する。

### 根拠

未知ノードへの対処をクライアントの実装詳細（`default: break`）に任せると、劣化の仕方がプラットフォーム間でずれる。**フォールバックを言語仕様の一部にする**ことで、編集者が「古いアプリではこう見える」を設計でき、エディタ上で警告も出せる。

## ADR-0007: バックエンド

### 決定

**TypeScript (Node 22) + Fastify**、PostgreSQL (JSONB) + S3 + CDN。オーサリングAPIと配信APIは同一コードベースだがデプロイ単位を分ける。

### 根拠

- エディタ (React/TS) とマニフェスト由来の型・検証ロジック・式評価の実装を**そのまま共有できる**。サーバ側でのドキュメント検証とプレビューレンダリングに同じコードを使えるのは大きい。
- 配信側の処理は「ドキュメントを引いて、ケイパビリティに応じて整形して返す」だけでCPUバウンドではない。言語性能は論点にならない。
- Kotlin/Spring を選ぶ合理性は「組織がJVM一色である」場合に限る。その場合は式評価の共有が失われる代わりに、Android実装をサーバと共有できる。**未確認の前提**なので roadmap の未決事項に記載する。

### 配信の形

- 公開されたドキュメントは**イミュータブル**。`/d/{documentId}/{versionId}` は内容アドレスで永久にキャッシュ可能 (`Cache-Control: immutable`)。
- クライアントが引くのは `/screens/{screenId}` で、これは現在の公開ポインタを解決して 200 か 304 を返す。短TTL + ETag。
- **ロールバックはポインタの差し替えのみ**（数秒）。

## ADR-0008: 適合性テスト戦略

3つのランタイム（Swift / Kotlin / TypeScript）の一致を機械的に保証する。

`spec/conformance/` に、実装非依存の JSON ケースを置く:

| コーパス | 入力 | 期待出力 |
| --- | --- | --- |
| `expr/` | 式文字列 + スコープ | 評価結果 (JSON値) またはエラーコード |
| `binding/` | ドキュメント + 状態 | 解決済みのプロパティ値 |
| `actions/` | 状態 + アクション列 | 遷移後の状態 + 発火した副作用の列 |
| `layout/` | ドキュメント | 正規化された描画ノード木 (レイアウト計算前) |
| `compat/` | ドキュメント + ケイパビリティ | 劣化後のノード木 |

各クライアントSDKのテストがこのコーパスを直接読んで実行する。**コーパスに追加せずに仕様を変更することを禁じる**（CIで検査）。

視覚的な検証は別建てとする: iOS は `swift-snapshot-testing`、Android は Roborazzi、Web は Playwright。こちらはプラットフォーム間の完全一致は求めず、各プラットフォーム内の回帰検出に用いる。

## 選定サマリ

| 領域 | 採用技術 |
| --- | --- |
| iOS SDK | Swift 6 / SwiftUI (iOS 16+), Swift Package Manager |
| Android SDK | Kotlin / Jetpack Compose (minSdk 24), Gradle |
| UI定義形式 | JSON + JSON Schema 2020-12 |
| 式言語 | 独自 `SpectreExpr` (非チューリング完全) |
| 単一の情報源 | `spec/component-manifest.json` + コード生成 |
| エディタ | React 19 + TypeScript + Vite + dnd-kit + Zustand/Immer |
| バックエンド | Node 22 + Fastify + PostgreSQL(JSONB) + S3 + CDN |
| 画像読み込み | iOS: Nuke / Android: Coil |
| 整合性担保 | 言語非依存の適合性コーパス + プラットフォーム内スナップショットテスト |
