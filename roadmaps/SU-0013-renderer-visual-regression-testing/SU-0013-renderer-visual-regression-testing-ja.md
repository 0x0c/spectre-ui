## はじめに

本項目は、2つのレンダラにビジュアルリグレッションテスト（Visual Regression Testing、VRT）を
追加します。1つはAndroidのJetpack Composeレンダラ、もう1つはiOSのSwiftUIレンダラです。

VRTの一式は、決められたUI定義ドキュメントを画像として描画します。そのうえで、コードと一緒に
登録した参照画像と各画像を比較します。この参照画像をゴールデンと呼びます。画面の見た目を変える
変更があれば、比較に失敗します。一式は、描画した画像と画素差分をビルドの成果物として出力します。

両プラットフォームは、1つのケース一覧 `spec/vrt/cases.json` を読みます。このファイルは `spec/` の
下、適合性コーパスの隣にあります。ゴールデン自体はプラットフォームごとに別のものです。Composeと
SwiftUIは設計上そもそも画面の描き方が違うので、画像は一致しません。ケース一覧を共有して保証するのは、
もっと狭いことです。どちらのプラットフォームも、同じ画面を同じ条件で検証します。

## 動機

Spectre UIは、描画のうち半分をすでに固定しています。適合性コーパスは `spec/conformance/` に
あります。ドキュメントとクライアントのケイパビリティを、3つのランタイムへ与えます。Swift、Kotlin、
TypeScriptの3つです。そのうえで、各ランタイムが返す解決済みレンダーツリーを突き合わせます。3つの
実装は、何を描くかについて一致します。適合性コーパスが届くのは、この解決済みレンダーツリーまでです。

解決済みレンダーツリーの下には、`RenderNode` を画素に変える段階があります。この段階は、
モディファイアの連鎖と、余白と配色のトークン表にまたがります。コンポーネントごとのComposeと
SwiftUIへの対応付けも、ここに含まれます。この段階が出力するものを何かと突き合わせる検証は、
どこにもありません。

レンダラを今日カバーしている検証は、もっと弱い性質しか見ていません。Androidでは
`:spectre-ui:testDebugUnitTest` がプロパティ抽出とトークン表を検証します。iOSでは
`SpectreUITests` が同じ2つの層を検証します。どちらもビューツリーを構築する手前で止まります。
`:spectre-ui:assembleDebug` と `xcodebuild build` の各ステップが示すのは、レンダラがコンパイル
できることだけです。何を描くかについては、どちらの検証も沈黙しています。隙間は3つの変更で見えます。
モディファイアの順序が入れ替わります。トークンが尺度の誤った段階を指します。バージョンの更新が、
MaterialやSwiftUIのデフォルト値をずらします。どれも、ライブラリが描くすべての画面を変えます。
ここまでに挙げた検証は、その間ずっと緑のままです。

この隙間は、自前の画面を持つアプリよりも本ライブラリで重く効きます。アプリはSpectre UIを組み込み、
ドキュメントを渡します。そのアプリのエンジニアは、渡すドキュメントをコードとして読みません。
描画の退行は、配信基盤がすでに公開した画面へそのまま届きます。アプリ側の再ビルドも要りません。
M1（SU-0002）がスナップショットテストを成果物に挙げたのは、この理由によるものです。その成果物は
未着手のまま残っています。M1に残る未完了項目のうち、レンダラを守るものはこれだけです。

端末ミラー（SU-0009）がこの隙間を埋めると考える読者もいるはずです。端末ミラーは、実機の描画を
作者の目の前に出します。同じ仕事に見えます。しかし、端末ミラーが答えるのは別の問いです。作者が
求めたその時に、1つのドキュメントの見た目を見せます。結果を読む人も必要です。退行の検証は、
プルリクエストごとに無人で走らなければなりません。誰も確認しようと思わなかった変更に対して、
落ちなければなりません。

## 詳細設計

1. **共有のフィクスチャとケース一覧。** `spec/vrt/` を追加します。`spec/vrt/screens/` に描画対象の
   ドキュメントを置き、`spec/vrt/cases.json` にケースを並べます。1件のケースは、対象ドキュメントと
   描画条件を指定します。描画条件は、密度非依存ピクセル単位の表示領域の幅と高さを含みます。テーマ
   （`light` または `dark`）とフォントスケールも含みます。両プラットフォームは、今日
   `spec/conformance/` を共有しているのと同じ形で、この1つのファイルを読みます。フィクスチャは
   `examples/screens/` から借りず、VRT専用に書き下ろします。フィクスチャは画素として安定して
   いなければならないので、リモート画像を持たせません。リモート画像は、ある実行では読み込めて、
   次の実行では読み込めないことがあります。フィクスチャを変えるのは、ゴールデンを変える意図が
   あるときだけです。
2. **Android側の一式。** `:spectre-ui` の既存のユニットテストソースセットに置きます。Roborazziは
   Robolectric経由で、ComposeツリーをJVM（Java仮想マシン）で描画します。そのため一式は、
   エミュレータや実機を使わずに走ります。既存のAndroidジョブと同じUbuntuランナーで動きます。
   各ケースは、宣言されたRobolectricの修飾子とフォントスケールを設定します。そのうえで
   `SpectreScreen` を描画し、PNG（Portable Network Graphics）画像を取得します。
3. **iOS側の一式。** 新しいテストターゲット `SpectreUISnapshotTests` を追加します。依存先は
   swift-snapshot-testingです。このライブラリは、SwiftUIビューを `UIHostingController` に載せて
   描画結果を取得します。この依存はテストターゲットにだけ宣言します。`SpectreUI` パッケージを
   利用するアプリが解決することはありません。一式はiOS向けにのみコンパイルし、`xcodebuild test` で
   iOSシミュレータへ走らせます。アプリが実際に出荷するSwiftUIはiOSのものです。同じビューをmacOSで
   描画して固定しても、目的の対象を固定したことになりません。
4. **ゴールデンの置き場所と2つの実行モード。** ゴールデンは、それを生成する一式の隣に置きます。
   Androidは `clients/android/spectre-ui/src/test/snapshots/` です。iOSは
   `clients/ios/Tests/SpectreUISnapshotTests/__Snapshots__/` です。検証モードは各画像を比較し、
   差分があれば失敗します。記録モードはゴールデンを上書きします。意図した見た目の変更を受け入れる
   手段も、記録モードです。記録モードで走らせ直し、その結果のコミットに現れる画像差分をレビュー
   します。
5. **2つのCIジョブ。** `android-vrt` と `ios-vrt` を追加します。各ジョブは、担当プラットフォームの
   ゴールデンがあれば検証モードで走ります。なければ記録モードで走り、記録した内容を成果物として
   出力します。最初の1組は、その成果物をコミットして用意します。`workflow_dispatch` の入力で記録
   モードを強制できます。意図した変更のあとにゴールデンを更新する手段が、この入力です。
6. **フィクスチャ網羅の検証。** `:spectre-core` のテストに追加します。マニフェストとフィクスチャを
   読みます。どのフィクスチャにも現れないカタログコンポーネントがあれば失敗します。この検証がないと、
   後からカタログへ足したコンポーネントは、ゴールデンを持たないまま出荷されます。そのことを知らせる
   失敗も起きません。読むのはJSONだけなので、Android SDKのない既存の `core` ジョブで走ります。

## 検討した代替案

- **エミュレータや実機で計装テストとして走らせる案。** 却下しました。CIでのエミュレータは1回の実行
  あたり数分を要します。端末外のレンダラなら避けられる不安定さも連れ戻します。起動の競合、
  アニメーションのタイミング、システムダイアログが戻ってきます。登録済みの画像と比較するには、
  決定的な描画が必要です。Robolectricは、固定されたAndroidのjarからそれを与えます。
- **Android側でRoborazziではなくPaparazziを使う案。** 却下しました。PaparazziはAndroid Gradle
  Pluginの内部に結び付いたGradleプラグインです。そのため、Android Gradle Pluginの更新がPaparazziの
  リリース待ちになりえます。Roborazziの取得関数は、テストのクラスパスに載る普通のライブラリです。
  本項目もその形で使うので、ビルドにプラグインは増えません。
- **同じケースのiOS画像とAndroid画像を突き合わせる案。** 却下しました。ADR-0001は、各
  プラットフォームでネイティブに見えることを狙って2つのネイティブレンダラを選んでいます。両者の
  画素の違いは、欠陥ではなく意図した結果です。プラットフォーム間の一致は適合性コーパスの担当です。
  適合性コーパスは、解決済みレンダーツリーの層でそれを担保します。
- **パッケージ依存を増やさず `ImageRenderer` でSwiftUIを描画する案。** 却下しました。
  `ImageRenderer` はUIKitのビュー階層の外でビューを描きます。スクロール領域、セーフエリア、
  ツールバーは、実行中のアプリと同じようには解決されません。`SpectreScreen` はこの3つを使って
  います。誤った描画を固定したゴールデンは、ゴールデンがない状態より悪いものです。
- **最初のゴールデンをCIの外で手作業から作る案。** 主たる経路としては却下しました。ゴールデンが
  意味を持つのは、後で比較する環境と同じ環境から生まれたときです。CIは、貢献者の全員が共有する
  唯一の環境です。XcodeとAndroid SDKを持つ開発者が手元で記録する道は残します。生成されるファイルも
  同じものです。
