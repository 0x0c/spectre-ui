## はじめに

マイルストーンM0は Spectre UI の仕様を凍結します。Spectre UI はサーバードリブンUI（Server-Driven UI、
SDUI）のためのクロスプラットフォームライブラリで、サーバが配信したUI定義ドキュメントを iOS と Android の
ネイティブSDKが解釈して描画します。M0は、コンポーネントマニフェスト、コンポーネントカタログ、
デザイントークン、式言語が固まり、マニフェストからのコード生成が動くようになった時点で完了します。
見積もりはフルタイム換算で3〜4人週です。

## 動機

以降のマイルストーンは、いずれもここでの決定の上に予算を費やします。M3の段階でカタログが足りないと
判明した場合、それは小さな手直しでは済みません。クライアントのレンダラ、生成された型、エディタの
パレット、そして既に作成されたすべてのドキュメントが、まとめて動くことになります。

したがって受け入れ基準は、名目ではなく挙動で置きます。実在する3つの画面、すなわち一覧、詳細、フォームを
手書きのJSONで表現でき、カタログが提供するもので足りるとレビューで合意できることです。この検証を経ずに
凍結したカタログは、楽観の上に凍結したカタログです。

## 詳細設計

1. **コンポーネントマニフェストのメタスキーマを設計します。** マニフェストは型とエディタ用メタデータの
   双方にとって単一の情報源なので、まずその自身のスキーマから着手します。
2. **コンポーネントカタログ v0.1 を確定します。** 凍結の前に、実在する3画面に対して紙上で検証します。
3. **デザイントークンを定義します。** 既存のデザインシステムがあるなら、二つ目の語彙を作るのではなく
   そこから写します。
4. **`SpectreExpr` の文法を確定し、**その適合性コーパスの初版を書きます。
5. **コード生成を作ります。** マニフェストから JSON Schema、TypeScript、Swift、Kotlin を生成します。
6. **適合性コーパスのランナーを3言語分作ります。**

## 検討した代替案

- **クライアントSDKを並行して始め、仕様は進めながら固める。** 却下します。生成された型はそれらのSDKの
  入力なので、並行作業は動く標的に対して積み上げられ、書き直しになります。
- **後から追加せずに済むよう、最初から大きなカタログを凍結する。** 却下します。前方互換性の設計により
  追加は安く、削除は高いので、カタログは検証用の3画面をまかなえる最小の集合から始めるべきです。
